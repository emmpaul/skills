# skill-authoring Specification

## Purpose
Defines how skill folders and agent-facing documents in this repository are written and kept, so every skill follows one authoring rubric and edits to a skill's wording never change what the skill does.

## Requirements

### Requirement: Root pointer to the authoring rubric
The repository SHALL have a root `AGENTS.md` that tells an agent to load the `writing-for-agents` skill before creating or editing any skill folder, `AGENTS.md`, or `CLAUDE.md`, and a root `CLAUDE.md` that loads `AGENTS.md`.

#### Scenario: Agent edits a skill
- **WHEN** an agent working in this repository is asked to create or edit a file under `skills/` or `shared/`
- **THEN** the always-loaded `AGENTS.md` names `writing-for-agents` as the rubric to load before writing

#### Scenario: Claude Code session
- **WHEN** a Claude Code session starts in this repository
- **THEN** `CLAUDE.md` brings the content of `AGENTS.md` into context

### Requirement: Planning rules apply the rubric
`openspec/config.yaml` SHALL carry rules that make every proposal, design, and task list for skill work apply the `writing-for-agents` rubric, and make every task that rewrites skill prose verify that behavior is preserved.

#### Scenario: New skill change
- **WHEN** an agent requests `openspec instructions` for the proposal, design, or tasks of a change that adds or edits a skill
- **THEN** the returned rules include applying `writing-for-agents` to the skill's description and body

#### Scenario: Rewrite task
- **WHEN** a task in such a change rewrites a skill's wording
- **THEN** the rules require that task's verification to check the skill's frontmatter and summary-block format and its spec requirements

### Requirement: Skills follow the rubric
Every `skills/<name>/SKILL.md` and hand-written reference file SHALL follow the `writing-for-agents` rubric. Descriptions keep only what triggers the skill. Steps come first and end on checkable completion criteria. Reference that only some branches need is disclosed behind a pointer. Rules are phrased positively, and each rule has one source.

#### Scenario: Description as pointer
- **WHEN** an agent reads a skill's frontmatter `description`
- **THEN** it states what the skill does and lists each distinct trigger branch once, without restating detail the body carries

#### Scenario: Shared reference
- **WHEN** a reference file is needed by several skills
- **THEN** its one source is in `shared/`, and the skill folders hold copies made by `scripts/sync-shared.sh` that `scripts/check-shared.sh` confirms match

#### Scenario: Generated or vendored files
- **WHEN** a file is generated by a script (the WCAG references) or vendored from another source (`writing-for-agents`)
- **THEN** it is changed only through its generator or source, not by a prose rewrite

### Requirement: Rewrites preserve skill interfaces
A change to a skill's wording or structure SHALL keep its behavior. It keeps the skill's name, flags, defaults, gates, confirmation prompts, and numeric limits, and every requirement in its main spec still holds. Summary blocks keep their marker, field names, and value formats byte for byte. Headings and anchors that other files link to keep working.

#### Scenario: Summary block consumed by another skill
- **WHEN** a rewrite touches a skill that prints a summary block another skill parses, such as `ep-review-summary`
- **THEN** the block's opening marker, field names, field order, and value formats are identical to before the rewrite

#### Scenario: Cross-file link
- **WHEN** a file links to a heading in another file, such as `references/side-paths.md#fixup`
- **THEN** the target heading still exists under the same anchor after the rewrite

#### Scenario: Condensed fallback copies
- **WHEN** a skill carries a condensed fallback of another skill's rules, such as the commit rules in `ep-orchestrate` or the side paths in `ep-babysit-pr`
- **THEN** the fallback still states the same rules as the skill it condenses
